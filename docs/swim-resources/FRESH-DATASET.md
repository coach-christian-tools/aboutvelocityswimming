# Fresh Velocity dataset

The implementation targets the named Firestore database `velocity-v2` in the existing Firebase project. Authentication remains project-wide. The original `(default)` database remains available, with no deletion or automatic migration. The browser defaults to `(default)` until an explicitly authorized frontend cutover sets `NEXT_PUBLIC_FIRESTORE_DATABASE_ID=velocity-v2`.

The code supplies the model, tooling and verification. The separately authorized October 7 release created and populated the production database, preserved a verified private archive, and cut over both localhost and `https://www.cutter.coach` to `velocity-v2`. A subsequent GoMotion review populated the current swimmer roster. See [the release record](releases/2026-10-07-fresh-dataset.md) for verified population and outstanding source access. Never copy historical roster, races, attendance, goals, film or analytics into the new database as new evidence.

## Model

- Business facts remain in teams, people, venues, documents, athletes, meets, swims and standards. Fresh attendance is one typed athlete/session entry. Legacy `results` is excluded from the active registry and denied in `velocity-v2`. Goals and Film Sessions are outside the active scope; `goals`, `film_sessions` and stored `records` have no active viewers or client permissions. Team records will be calculated from `swims`, without a second stored collection. Historical archived data is retained.
- Private `sources` identify a URL, local authoritative export, manual declaration, or email message reference. They store scope, retrieval method, interval (30 days by default), last attempt, successful scope check and current revision. Disable a source instead of deleting its history.
- `source_bindings` identify an exact record path, covered fields, context (such as a season), and priority. Lower numbers win only within that scope. Null priorities, ties, different contexts and protected changes require review.
- `record_provenance/{sha256(recordPath)}` stores accepted evidence per field, required field coverage, failed checks, successful verification, actual fact changes and open disagreement IDs. `events` preserve check/decision/reversal history; `disagreements` preserve competing claims and resolution pointers.
- `sources/{sourceId}/checks` are immutable retrieval attempts. `sources/{sourceId}/revisions/{contentHash}` identify immutable private Storage bytes. Identical bytes reuse the archive, while every attempt retains a check. Retrieval alone never verifies a fact.
- Each business write has an external, manual, derived or audit origin. Projections carry private derivation provenance; public profile/best/standards documents carry no evidence. A manual declaration has no external verification date.

An unchanged supported observation advances only its checked fields. Failed retrieval, incomplete verification or failed archival preserves accepted facts and earlier successful check dates, with attention reasons. Due dates are computed from each accepted field's check and interval; collection attention search is explicitly limited to loaded rows. Stored `needsAttention` filters cover failures and unresolved disagreements, not a whole-database time-based query.

The read-only `/tools/swim-resources/admin/maintenance` queue adds overdue checks, missing coverage, failures, disagreements and open review questions, explicitly limited to the loaded page of 100 records or sources. Private `record_provenance.reviewQuestions` retain uncertainties which do not yet assert a competing fact, such as an ambiguous deadline zone or a standards validity date. Questions never advance successful check dates or fact-change dates. Their updates/resolutions remain in immutable provenance events and survive ordinary checks, reviewed Import and reversal.

To annotate or explicitly resolve a question, prepare private JSON `{ version: 1, id: "unique-operation-id", target: { project, database: "velocity-v2" }, updates: [{ targetPath, id, question, fields, status: "open" | "resolved", evidence: [{ sourceId, revisionId, checkId, checkedAt, excerpt }], resolution? }] }`. Preview with `node scripts/swim-resources/review-questions.mjs --project <id> --database velocity-v2 --input backups/...`. Writes require matching `--apply --confirm-project <id> --confirm-database velocity-v2`. Each update requires an existing record/provenance and published capture/check. Resolving requires an existing open question and a supporting explanation; use a new operation ID for each later review or reopening. A replay is idempotent and altered reuse is rejected. An annotation or resolution does not import facts: factual changes still follow reconciliation or reviewed Import.

Public bests start empty until new verified races exist. Best-time projection refresh and recovery remain supported; stored record-board rebuilding is removed. A future team-record display must calculate from verified `swims` directly. In the fresh database public standards pages use current imported sets tagged `category: motivational` or `championship`; archived bundled standards are only a fallback for the original database.

## Manual tools

Use Node 24. All remote tools require `--project` and `--database`. Writes additionally require `--apply --confirm-project <same-id> --confirm-database <same-id>`. Choose ADC, `--key` outside the repo, or a verified Velocity `--firebase-cli` account. These examples describe separate release operations, not permission to execute them.

Local staging, captures and pending imports live under `backups/imports/<project>/<database>/`. Dataset archives live under `backups/archives/<project>/<database>/`. These ignored paths have private directory/file permissions and are excluded from Next's production traces. Old unqualified batches are never discovered by the new workflow; ImportBatch v1 is rejected.

1. Prepare a private source configuration with matching `target`, `sources` and `bindings`. Register/preview with `node scripts/swim-resources/register-evidence.mjs --project <id> --database velocity-v2 --config backups/.../sources.json`. Apply only with matching confirmations. Sources omit `intervalDays` to use 30; bindings omit `priority` to remain unranked. No priority is inferred from a URL or source name.
2. Collect a registered public HTTP source with `node scripts/swim-resources/collect-sources.mjs --project <id> --database velocity-v2 --source <source-id>`. `--due` stages up to 100 due sources. Each capture is bounded to 20 MB, three redirects, and a 30-second request timeout; private network destinations are rejected. Collection stages local files only. Access failures stage failed attempts instead of changing existing facts.
3. For newly obtained exports use `--input backups/... --content-type text/csv`. Email retrieval uses `retrieval: email` and a small JSON object containing provider, messageId, optional account/reference and a relevant excerpt of at most 4,000 characters. Whole messages, headers, attachments and mailbox dumps are excluded. Source access must be obtained separately; the tool has no mailbox crawler.
4. Read the capture and add explicit observations to its bundle: `targetPath`, `claims`, and `evidence` containing sourceId, revisionId, checkId, checkedAt, fields, context and excerpt. The hash/check/time must match the capture. Partial observations list only their covered fields. A capture with `verificationError: incomplete_parse` archives bytes but flags affected bindings and accepts no facts. An empty observation list archives retrieval without claiming verification.
5. Preview with `node scripts/swim-resources/reconcile-evidence.mjs --project <id> --database velocity-v2 --bundle backups/.../bundle.json --bucket <private-bucket>`. Apply additionally requires matching confirmations. Immutable archives publish before facts are accepted. Existing directory facts can reconcile according to explicit scoped authority. New entities and roster/race changes stay held for reviewed Import. Facts, provenance, disagreement resolutions and receipts commit together per record. Retries skip committed events. Reconciliation receipts appear under `import_batches/auto_<hash>/changes` and use the same guarded reversal as reviewed imports.
6. Create evidence-backed v2 JSON, then stage with `node scripts/swim-resources/prepare-import.mjs --project <id> --database velocity-v2 --input backups/.../import.json`. It verifies published source checks before placing the file in the matching pending directory. Open Import, preview, and select up to 25 additions, changes or unchanged checks. Applying a check does not rewrite facts or advance their change date. Dependencies and evidence are checked again transactionally.

The roster producer is `node scripts/swim-resources/update-roster.mjs --project <id> --database velocity-v2 --source <id> --check <id> --csv backups/.../current-roster.csv --encoding utf8 --complete`. Its CSV hash must match a published capture. It stages v2 only and refuses direct writes. Other producers use the shared v2 schema, including `standard` rows with metadata/category and validated `cutsByTier`. Legacy direct import/migration scripts reject `velocity-v2`.

## Initial population order

Run `node scripts/swim-resources/prepare-velocity-seed.mjs --project <id> --database velocity-v2` to stage a manual identity declaration based on the user's approved Velocity name. Register its source, archive its bundle, prepare its import JSON and review it in Import. It does not invent a website, contacts, roster or verified performance data.

Then obtain current authoritative roster/contacts/venues and import them with explicit identities. Import parent entities before their dependents. Athlete-linked people require an existing athlete; subsequently link the athlete back to its person. Meets reference existing venues/host teams/contacts; packets become document records with source and revision pointers. Current standards are separately reviewed. Field checks do not transfer verification to omitted fields or to other records.

## Separate release actions

1. **Archive and restoration gate.** Pause old writers. Run `node scripts/swim-resources/archive-dataset.mjs --project <id> --database '(default)'` for a private local snapshot. It enumerates all root/subcollections, including orphan parents; preserves timestamps, coordinates, bytes, special numbers and qualified references; verifies per-collection counts and repeated fingerprints; downloads referenced Firebase/GCS archive objects and checks the dataset again after file capture. Any missing file or changed dataset fails the export. A URL alone is not a preserved historical document: verify that all relevant prior captures exist before cutover. Publish the verified archive to a private bucket with `--bucket` and matching apply confirmations. Cloud files are hash-deduplicated, verified, and written under `legacy-archives/<project>/<database>/<archive-id>/` before the completion manifest is published. No original objects are deleted.
2. Test **that exact manifest** using demo Firestore/Storage emulators and `node scripts/swim-resources/restore-archive.mjs --project demo-restore --database restore-test --manifest backups/.../dataset.json` plus matching apply confirmations. The tool refuses live restoration or the fresh target, checks every local file, recreates archived files in emulator Storage, restores document types and compares the resulting fingerprint/count. Retain the report and private archive externally before cutover. Qualified references deliberately retain their original project/database identity.
3. **Provisioning.** Create `velocity-v2` explicitly in the existing project using the [Firebase database guide](https://firebase.google.com/docs/firestore/manage-databases), with a reviewed location/type and delete protection. Do not clone the old dataset. Record the project/database identity.
4. **Rules and Storage configuration.** Deploy only the fresh database rules/indexes with the confirmed target; do not blindly deploy the multi-database configuration to the original database. Configure a private archive bucket, deny public IAM/ACL access, use `storage.rules`, and allow only the actual frontend origins in Storage CORS for authenticated blob reads. Archives have attachment disposition, content hashes and no Firebase download tokens. Test anonymous Firebase and GCS URLs fail, and verified coaches can download exact revisions. Firestore rules cannot enforce bucket IAM privacy.
5. **Population.** Register current sources, archive captures, import the Velocity identity and reviewed current data. Verify initial counts, relationships, private provenance, current standards and deliberately empty performance/history collections. Unavailable sources stay unpopulated. No scheduler or embedded AI is enabled.
6. **Frontend cutover.** Only after the archive/restore and new dataset gates pass, set the named database environment variable and rebuild/release the intended frontend. Firebase web configuration and coaching Auth accounts stay project-wide. Verify desktop/mobile admin, Import recovery, public empty bests and rules against the actual target. The emulator does not enforce production indexes/transaction limits; check these in the authorized pre-release environment.
7. **Rollback.** Set the variable back to `(default)` or omit it, rebuild the frontend and verify original data is available. Original rules/data/files remain intact. Keep fresh pending imports qualified to `velocity-v2`; they cannot enter the old workflow. No automatic archive retention deletion is provided.

## Local verification

`npm run verify` runs lint, types, synthetic policy/service tests and the production build. `npm run test:rules` runs Firestore and Storage emulators, including actual Import apply/recovery/reversal, private evidence access, immutable archives, target isolation and lossless restoration.

The installed Firebase CLI cannot initialize multiple database rules from the production configuration. Local tests use `firebase.emulators.json`, then explicitly load the named rules with `scripts/swim-resources/lib/emulator-rules.mjs`. For local UI development start `firebase emulators:start --config firebase.emulators.json --project demo-cutter-coach --only firestore,auth,storage`, then run `FIRESTORE_EMULATOR_HOST=127.0.0.1:8088 node scripts/swim-resources/load-emulator-rules.mjs --project demo-cutter-coach --database velocity-v2` before browsing. Implicit named databases otherwise use [open emulator rules](https://firebase.google.com/docs/emulator-suite/connect_firestore). This loader refuses live projects and non-local hosts.
